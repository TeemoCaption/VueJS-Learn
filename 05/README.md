# Vue 元件資料流：Props、事件與 `v-model`

這次的核心不是「怎麼把畫面拆成元件」，而是拆完之後，資料應該怎麼流動。

當一個元件需要顯示外部資料、回報使用者操作，或編輯外部資料時，Vue 分別提供了三種清楚的溝通方式：Props、事件與 `v-model`。

## 先記住這張地圖

```text
讀取資料：父層 ── Props ──> 子層
回報操作：父層 <── 事件 ── 子層
編輯資料：父層 <── v-model ──> 子層
```

三者不是互相取代的語法，而是對應不同需求。

| 你要做什麼？ | 應優先使用 |
| --- | --- |
| 顯示父層提供的資料 | Props |
| 通知父層某個操作發生 | 事件 |
| 讓子層直接編輯父層狀態 | `v-model` |

---

## 一、Props：把資料交給負責顯示的元件

Props 的角色很單純：父層把資料交給子層顯示。它適合商品資訊、人物資料、課程資料、標籤清單等「子層需要看，但不擁有」的資料。

### 什麼時候使用？

當資料的來源與更新決策都在父層，而子層只需要依照資料呈現畫面時，就使用 Props。

例如，一張卡片需要顯示名稱、價格與庫存，但「價格怎麼改、庫存從哪裡來」都不是卡片的責任。卡片只負責顯示。

### 設計時的三個問題

1. 這個資料真的需要由外部提供嗎？
2. 它的型別是什麼？數字、布林值、陣列與物件都要清楚。
3. 沒有提供時，元件應該顯示預設值、空狀態，還是直接要求必填？

陣列與物件的預設值要特別小心：每個元件實例都應擁有自己的預設資料，不能意外共用同一份可變動物件。

### 最重要的規則

**子層不要直接修改 Props。**

因為資料的擁有者在父層。若子層直接改，畫面也許暫時會動，但資料從哪裡改、誰負責維護會變得不清楚。子層想要求修改時，應使用事件或 `v-model`。

---

## 二、事件：把「發生了什麼」告訴父層

事件適合表達使用者操作，例如點擊加入、切換狀態、刪除資料或增加數量。

事件的精神不是「子層命令父層做事」，而是「子層回報發生了一件事」。父層收到後，自己決定要不要更新資料、顯示訊息或呼叫服務。

### 什麼時候使用？

當子層只需要回報一個明確動作，而不是持續編輯某份資料時，使用事件最合適。

例如按下「加入」後，子層只要回報哪一筆資料被加入；至於購物車怎麼更新，應由父層決定。

### 事件設計原則

- 名稱要描述已發生的動作，例如「加入」「刪除」「切換」。
- 需要父層辨識目標時，事件可以帶資料，例如被操作的物件或數值。
- 不要讓子層直接知道父層的處理細節。

這種分工讓同一個元件可以被不同頁面重複使用；不同頁面只要替事件接上不同處理方式即可。

---

## 三、`v-model`：讓子層編輯父層擁有的資料

`v-model` 適用於「輸入後就要同步更新」的情境，例如文字欄位、搜尋條件、留言內容、書名或會員資料。

它解決的問題是：資料屬於父層，但輸入控制項在子層。使用者在子層輸入後，父層必須立刻取得新值。

### 什麼時候使用？

請用這個判斷：

- 只顯示資料：Props。
- 按一次按鈕、回報一次結果：事件。
- 使用者持續輸入，父層狀態必須同步：`v-model`。

### `defineModel` 的意義

在自訂元件中，`defineModel` 可以把「接收目前值」與「回傳更新值」整理成一個可直接雙向綁定的模型。

它不是跳過資料流，而是把原本要手動處理的 Props 與更新事件包裝起來。因此資料仍然由父層擁有，子層只負責編輯。

### 單一與多個模型

若元件只編輯一份資料，例如搜尋文字，使用一般 `v-model` 即可。

若元件同時編輯多份彼此獨立的資料，例如姓名、信箱與年齡，應使用具名 `v-model`。這樣每一個欄位都有明確的資料意義，避免把所有值混在同一個模糊的模型中。

數字輸入時，記得處理型別轉換；輸入框取得的值常是字串，後續若要計算年齡、數量或價格，就需要轉為數字。

## 四、狀態放哪裡，取決於誰要使用它

資料流設計常見的困難，不是語法，而是狀態位置選錯。可以用使用範圍判斷：

| 狀態的使用範圍 | 合適位置 |
| --- | --- |
| 只有一個元件需要 | 元件內的 `ref` |
| 親子元件需要共同協作 | 父層狀態搭配 Props、事件或 `v-model` |
| 可由其他資料推導 | `computed` |

### 區域狀態

一張卡片的展開與收合、單一按鈕自己的點擊次數，通常只影響自己，應留在元件內。每次建立新的元件實例時，這些狀態也會各自獨立。

### 共享狀態

多個元件必須看到同一份資料時，才需要共享狀態。簡單情境可以放在外部模組；狀態越靠近真正使用它的地方，通常越容易理解與維護。

### 衍生狀態

若一個值可以從其他資料算出來，就不應再存一份副本，而應使用 `computed`。

例如完整名稱可以由姓氏與名字組合而成。這樣只要來源資料更新，結果會自動保持正確，也能避免兩份資料不同步。

## 五、常見錯誤

### 1. 把資料修改權交給錯的人

子層直接改 Props，或不相關的元件隨意修改共享狀態，都會讓資料來源難以追蹤。先確認誰是資料擁有者，再設計更新管道。

### 2. 把事件與 `v-model` 混用得沒有目的

一次性的操作用事件；連續輸入、需要即時同步的資料用 `v-model`。兩者都能傳資料，但使用情境不同。

### 3. 把所有狀態提升到最上層

這會讓父層變成難以維護的「大型控制中心」。只屬於單一元件的狀態，應留在該元件內。

### 4. 忘記型別與空狀態

數字與布林值誤當字串、列表沒有資料、選填資料缺失，都是常見的畫面錯誤來源。元件設計時要先想好這些邊界情境。

---

## 最後的判斷口訣

> 資料給子層看，用 Props；
> 操作發生要回報，用事件；
> 子層要編輯父層資料，用 `v-model`；
> 多處都要共用，再考慮共享狀態。

這四句話能幫你在設計 Vue 元件時，先選對資料流方向，再開始寫程式。
